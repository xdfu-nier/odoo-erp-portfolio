# 工业配件分销 ERP：需求基线 0.1

状态：需求基线0.1已于2026-10-26获得项目负责人确认，按本文件进入M0开发环境验证，再开发M1报价审批。功能尚未交付。

## 1. 业务目标

为一家销售轴承、传感器和标准件的贸易企业管理从报价到退货开票的流程。销售、采购、仓库和财务围绕同一张订单协作，能够回答：订单是否可以确认、缺多少货、采购到哪一步、交了多少、开了多少发票、退货是否完成。

公开案例及需求推导见[调研记录](../discovery/case-research.md)。下面的阈值和业务政策是本项目规则，不是从案例中获得的客户原始需求。

## 2. 首版边界

业务验收使用一个公司、一个仓库、人民币和按实际交付数量开票的库存商品。另建一家独立公司用于权限隔离测试，不实现公司间自动交易。

包括客户/供应商与商品主数据、销售审批、采购来源关联、分批收货与交货、可再销售商品退货、客户发票和贷项通知单、订单追踪。

外部订单接入安排在业务闭环之后。制造/BOM、维修工单、质检隔离、商城、税控发票、银行自动对账及跨境本地化不进入本轮范围。这里的“开票”指 Odoo 客户发票，不是税控系统开具的法定电子发票。

## 3. 角色与操作范围

| 角色 | 允许的主要操作 | 约束 |
| --- | --- | --- |
| 销售 | 维护客户、建立本人报价、申请审批、查看本人订单进度 | 不能自行审批、修改审批结论或执行仓库/财务操作 |
| 销售经理 | 查看公司订单、审批及拒绝 | 不能审批本人创建、本人负责或本人提交的订单 |
| 采购员 | 维护供应商、查看需求与在途、建立采购单 | 不能放行销售审批或替仓库确认收货 |
| 仓库员 | 收货、发货、创建和处理退货 | 只能操作有权限公司和仓库的单据 |
| 财务 | 建立/过账客户发票、贷项通知单并查看业务来源 | 不能通过修改库存数量完成财务调整 |
| 接入账号 | 提交和查询已授权来源的订单导入任务 | 不授予管理员、审批或跨公司权限 |

同一人可以被明确授予多个角色，但权限组合不能绕过禁止自审规则。验收使用分开的角色账号，管理员不作为业务权限验证账号。

## 4. 业务需求

| 编号 | 用户需求与规则 | 来源 |
| --- | --- | --- |
| REQ-001 | 商品具备 SKU、名称、计量单位、供应商、销售价和开票策略。客户/供应商具备业务编号与公司归属。外部映射必须唯一匹配，未找到或多条匹配时拒绝处理，不自动创建主数据。 | CASE-03；本项目规则 |
| REQ-002 | 自定义模型、关联字段、界面、导入和查询均按公司授权执行。通过接口传入其他公司 ID 也不能越权。 | CASE-01；本项目规则 |
| REQ-003 | 公司可配置审批阈值，初始值为未税金额 ≥ 50,000 元或任一有效商品行折扣 > 10%。满足任一条件必须先申请、再由其他有权人员审批，才可确认订单。未触发阈值的报价可正常确认。 | REF-01；本项目规则 |
| REQ-004 | 报价在提交或审批后，修改客户、公司、币种、付款条件、交期或商品行的商品/单位/数量/价格/折扣/税，审批立即失效并要求重新提交。审批字段不能经直接 ORM/API 写入伪造。 | 本项目规则 |
| REQ-005 | 采购员从预测库存、在途数量及销售需求判断补货；首版手工生成采购单，并明确关联来源销售订单。关联用于追踪，不代表采购货物被独占分配给该订单。不自研自动净需求算法。 | CASE-01；本项目规则 |
| REQ-006 | 使用 Odoo 标准库存预留和收发货流程，支持分批收货、分批交付与后续补交。不得通过直接改库存或订单状态跳过标准单据。发货不能超过实际可交数量；首版不允许业务发货形成负库存。 | CASE-01；本项目规则 |
| REQ-007 | 采用交付数量开票，发票数量不得超过当前可开票数量。客户退货必须更新原销售订单交付数量；先完成实物退货，再对原已过账发票开具关联销售行的贷项。禁止先贷后退、重复/超量退货及超量贷项，不得仅改数量汇总数字。 | 本项目规则 |
| REQ-008 | 从销售订单查询采购、收发货、退货、发票和贷项通知单；分别展示实际交付、退货、净交付、已开票及已过账数量/金额，保留原始单据，不压成一个总状态。 | CASE-01、CASE-02 |
| REQ-009 | 结构化外部订单先进入持久化接收任务，记录来源、公司、外部单号、载荷摘要及处理状态。接入不直接确认销售订单，仍执行销售审批规则。 | CASE-02；本项目规则 |
| REQ-010 | 公司 + 来源 + 外部单号是幂等键。相同业务内容重复提交返回已有任务；不同内容返回冲突，不覆盖已经生成的订单。数据库唯一约束覆盖并发请求。 | CASE-02；本项目规则 |
| REQ-011 | 接收任务处理失败时保留原因、尝试次数和处理时间；可修复的主数据问题经修复后人工重试。一次任务处理中的业务写入失败应完整回滚，不留下半张销售单。 | 本项目规则 |
| REQ-012 | 申请、审批、拒绝、改单失效和导入重试记录操作人、时间、原因及相关单据；普通业务用户不能修改审批历史或导入原始载荷。 | CASE-01；本项目规则 |
| REQ-013 | 新环境可按文档安装、初始化、升级模块、备份及恢复；新增依赖、数据库和缓存限定在项目内，开发过程无需 Docker。 | 用户约束 |
| REQ-014 | 对订单追踪与导入做可复现的性能检查，保留数据规模、机器配置、SQL 次数和耗时；尚未测试的指标不得写成成果。 | CASE-03；本项目规则 |

“不超过可交/可开票数量”和“禁止负库存”需单独确认标准 Odoo 能力与定制差异，不能只靠按钮显隐或假定标准流程已经限制。

## 5. 审批与修改

报价可有草稿、待审批、通过和拒绝的审批状态，标准销售订单状态仍由 Odoo 管理。审批申请保存当前内容快照；审批与确认时重新核对快照。相同订单不能由并发操作同时形成两个有效审批结论。

拒绝必须填写原因，销售修改后可重新申请。经理只审批，不代替销售确认。已确认订单的关键商业字段在首版禁止直接变更；由取消未执行部分或退货/贷项流程处理，不覆盖已发生业务。

本轮策略仅针对公司本位币配置的首版验收；多币种审批政策单独扩展，不隐式将不同币种金额与人民币阈值比较。

所有影响审批的订单修改及销售行新增、修改、删除，都必须与审批/确认使用同一订单并发控制协议。政策变更也必须使旧政策的审批不能继续放行。不能只给确认操作加锁而允许其他路径绕开。

## 退货与贷项政策

首版处理可再销售商品，退货必须引用原交付库存移动并更新销售订单数量。累计退货不能超过原实际交付扣除既有退货的数量。贷项必须关联原销售行和已过账客户发票；可贷数量同时受“已退货未贷数量”和“原已过账发票未贷数量”约束，草稿贷项也占用额度，取消后才释放。

先建贷项、后补退货的路径在首版被服务端拒绝；此约束针对本项目销售订单，不改变其他非项目财务调整的标准用途。原发票单价和折扣作为贷项依据，未经处理的退货不允许通过重复开票抵消。退货和贷项的顺序及数量需经过独立验收。

## 6. 典型订单

客户购买 100 个轴承，标价 100 元，折扣 15%，未税订单金额 8,500 元。期初可用库存 40 个，需要采购 60 个。因折扣触发审批，销售先申请，经理审批后销售确认。

供应商先送 30 个，仓库累计可用 70 个，先发货 70 个并开票 5,950 元；余下 30 个收货后再发货，补开发票 2,550 元。客户之后退回 10 个可再销售商品，处理回库和 850 元贷项通知单。

最终净交付 90 个、净过账客户发票 7,650 元、剩余库存 10 个。测试场景不含税、运费或已收款；这些数字是验收预期，不是已实现结果。

## 7. 可交付标准

上述规则必须落到相应角色下的 Odoo/PostgreSQL 集成测试、完整业务验收和发布记录。配置单元测试、菜单截图或编译通过，不能作为业务需求完成证据。逐条用例见[验收计划](../quality/acceptance.md)。
