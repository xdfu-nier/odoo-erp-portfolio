# M2 订单履约：固定源码下的工程设计

本设计细化已确认的 REQ-005—008 和 UAT-008—013、025—027，不改变需求基线。
开发基线为 M1 合并提交 `8b6f9cf`：87 个真实 Odoo 测试及13个辅助测试通过。
本文件是实现方案，下面描述的行为尚未交付；实际结果另行记录。

## 范围与交付拆分

继续复用标准 PO、picking、move、quant、account.move 和账务行。
先实现采购来源/库存约束，再实现发票/退货贷项，最后完成只读追踪与本地验收数据升级。
三个阶段分别保留可复现测试、独立规格/质量审查和 PR；完整100→90场景对平后才算M2验收。

不增加库存账、会计引擎或自动采购计划器。采购仍由采购员判断标准在途/库存信息后手工建立，
来源关联只用于追踪，货物仍在仓库公共库存池中。

新增系统设置管理员控制的公司策略 `portfolio_fulfillment_enabled`，默认关闭。
它与价格审批、主数据策略独立，启用后公司的标准菜单和 API 都执行履约约束。
普通角色不能启停，也不能通过逐单字段或调用方 context 退出。
现有验收公司不会被普通重跑工具自动修改；M2完整就绪后通过明确的本地升级操作启用。

## 采购来源及角色

PO新增 `portfolio_source_sale_id`，与同公司已确认SO关联，不能改变原生路线/库存分配。
使用独立字段而非原生 POL.sale_line_id：sale_purchase_stock 会将后者及路线传播给收货移动，
带有超出“来源追踪”的 MTO/服务采购语义。

创建/修改关联及采购确认/经理批准均校验来源公司、当前状态及操作者读取权限。
PO提交/确认后不能替换或清除来源；已确认单据的公司转移也不能绕过策略。
采购员获得公司内符合条件来源订单及其行的只读权限，不获得销售修改权限。
保留原有销售、仓库、财务的角色边界；不存在通过全局sudo查询或写业务单据的捷径。

## 库存事实与并发

固定源码允许负库存：`stock.quant._update_available_quantity` 使用
`FOR NO KEY UPDATE SKIP LOCKED`，必要时另建quant；只锁单据或只比较未预留数量会出错。
比较对象是实际源位置、商品、批次/包裹/货主的实物数量，按原生单位换算与精度处理。
本单自身预留不能从可供本单发货数量中再扣一次。

启用公司的库存完成操作使用统一顺序：公司ID、相关SO ID、库存记录ID。
公司加锁后更新受保护的技术序列 `portfolio_stock_revision`，使已建立repeatable-read快照的
竞争事务产生真实序列化冲突，并由Odoo新事务重试。只执行 `SELECT FOR UPDATE` 不足以消除旧快照。
序列更新只触及技术字段；授权、实际操作者公司范围在SQL之前检查，不直接写库存或单据状态。

库存完成由仓库角色执行。核心扩展放在原生 move/move-line 完成路径，保留预留、批次检查、
补交和盘点。完成后再次核对受影响的内部源库存非负；失败在保存点内回滚，不能留下完成一半的单据。
内部移库、报废或供应商退回同样不能通过从空位置出库制造可继续发货的虚假库存。

保护公共ORM路径：直接创建/写入done状态，向已完成picking追加done移动/行，
修改已完成移动的数量、商品、公司、位置、销售行/退货来源及to_refund，以及quant.quantity直接写入。
原生更新器使用绑定游标、操作者和公司范围的私有Python执行能力；不信任inventory_mode等可伪造context。
标准 `inventory_quantity → action_apply_inventory → move._action_done` 仍可生成合法盘点。
未启用公司保留原生行为。

## 发票、退货及贷项

实际授权额度从done库存移动和真实账务行推导，不依赖可由ORM覆盖的SO汇总缓存。
保护物理销售行的数量计数及反向invoice_lines关系，防止绕过账务行校验修改关联。
普通销售不能借原生SO的sudo开票桥接取得财务权限；明确检查原始uid的真实角色和允许公司。

正常客户发票不得超过实际可开票量。草稿与过账分别展示，非取消草稿占用额度，取消释放。
禁止通过直接写posted状态或直接修改/迁移账务行绕过过账与额度检查；保留标准分录平衡、账户、币种及原生过账。

客户退货必须引用同公司/商品/销售行的真实已完成客户交付，来源/去向位置及单位兼容，
并强制 `to_refund=True`。完成时重新限制累计已退数量不超过原交付。
不能靠关闭“更新销售数量”或改写已完成事实改变净交付。

贷项只允许在实物退货之后，保留原已过账发票及销售行。
额度同时受销售行“已退未贷”与原发票“已过账未贷”约束，所有非取消草稿贷项也占用。
创建、改单、删除、取消、重置及过账检查使用同一并发协议；不同原发票也可能竞争同一销售行退货额度。
原发票撤回/取消时不能留下失去来源依据的有效贷项。

标准整张冲销会先复制70/30数量再允许编辑，违反初始草稿额度。
提供直接创建有界部分贷项的动作/向导，按原行价格、折扣、税、单位、币种构造10个的草稿，
保留 reversed_entry_id 和 sale_line_ids，继续调用原生过账。不提供临时跳过检查的context。

## 追踪及本地会计准备

追踪使用原有SO→picking、PO→receipt、backorder、return/origin及invoice/reversed_entry关系。
分别显示毛交付、实物退回、净交付、草稿占用、已过账数量与金额，不合并成一个业务状态。
已过账金额来自实际会计凭证的符号金额，不以当前售价乘交付数量代替。
角色查询使用有边界的只读ACL/规则，不添加业务写权限，不暴露他公司记录。

现有PARTS-A为CNY且已有期初盘点，不能盲目加载generic_coa：固定源码会将空账套公司的币种改为US财政国币种。
本地升级先核对原19个数据标识和盘点凭据，再以独立M2命名空间准备最低限度的原生CNY账户/销售日记账。
已有会计数据、不同来源同名记录或不一致设置时拒绝自动处理，保留既有记录/用户编辑，不重载账套。
这是虚构数据的验收准备，不声称实现法定中国税务本地化；商品和交易行明确无税。

## 验收证据

正向场景：库存40；采购60先收30，交70开5950；再收30交30开2550；退10贷850。
期末库存10、净交付90、净过账客户发票7650。采购、仓库、财务分别由实际角色执行。

反例覆盖：负库存、原始状态/数量/关联绕过、跨公司来源、错误/超量退货、先贷后退、
双草稿抢占、取消释放及重置再次占用、原发票撤回、原生单位舍入、不同SO争同一库存。
并发使用独立事务、已预加载旧快照、可观察的PostgreSQL锁等待及序列化重试后的最终校验。
所有数据库测试由主会话独占运行，开发库与回归库分离。
