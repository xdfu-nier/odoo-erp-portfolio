# 开发与交付流程

| 里程碑 | 交付内容 | 退出条件 | 当前状态 |

## 2. 开发入口

需求必须有编号、业务规则、Odoo标准能力差异和验收场景。先完成需求/方案评审，再为当前里程碑编写实现计划；未进入当前里程碑的事项保留在任务清单中，不提前堆砌空模型和菜单。

M0 可与需求文档评审并行准备，但业务规则未确认前不实现审批、接口或库存约束。任何无法复现的业务假设标为待验证，不标为已满足。

## 3. 分支和代码评审

- 需求与方案使用 `docs/*` 分支，通过 PR 提交评审。
- 业务功能使用 `feat/*` 分支，修复使用 `fix/*`，每个分支只完成一组有明确验收条件的需求。
- PR 写明需求编号、行为变化、验证命令和结果、数据库升级/回退方式及未解决问题。
- PR 通过测试与审查后再合并，不以“代码已生成”或“菜单可见”作为完成标准。

## 4. 测试与验收

开发前先写能复现业务规则的测试，再实现服务端逻辑；界面隐藏只帮助操作，不承担业务权限约束。自定义模型和标准单据的衔接必须在真实 Odoo 环境验证。

配置测试与代码编译属于基础检查，CI名称和发布记录应区分它们与业务集成测试。权限测试使用普通角色，多公司和并发测试必须执行，不能由管理员账号的成功操作替代。

## 5. 版本、升级与运维

固定上游 Odoo 版本和模块版本。发布前执行新库安装与旧版本升级验证；新增字段可升级不代表存量数据已正确迁移。数据库备份、文件存储备份和源码版本需要能对应恢复。

恢复验证在独立数据库和文件目录执行，先核对记录数量、库存与发票，再决定上线。开发项目不注册系统服务，不安装全局依赖，不把真实凭据和业务数据提交到公开仓库。
