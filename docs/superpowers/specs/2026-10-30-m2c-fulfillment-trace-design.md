# M2c 履约追踪与本地财务验收设计

## 目标

在 M2b 已完成的开票、退货和贷项控制之上，补齐开发环境中的只读履约追踪、显式本地 CNY 会计准备和真实业务角色页面核对。这个阶段服务于本地作品集验收，不把虚构数据包装成法定中国税务或企业生产数据。

## 设计

只读追踪复用 Odoo 原生销售单、采购单、库存移动、退货来源、发票和冲销关系。用户从销售单查看一个只读追踪页面，页面展示采购来源、收货/交付及 backorder、退货来源、毛交付、实物退回、净交付、草稿/过账数量及实际过账金额。数量来自已有 `financial_policy.physical_facts` 与 `financial_policy.financial_facts`，金额来自关联已过账商品账务行的实际符号金额；不新增可写数量账本，也不把整张多销售单发票金额重复计给每张销售单。追踪入口按原始调用者的销售、采购或财务读取权限过滤公司和来源。

本地 CNY 会计准备使用项目内命令和隔离命名空间。命令先验证实际数据库连接为本地 loopback、目标为开发库或指定回归库、模块已安装、PARTS-A 的19个验收标识及40件期初盘点证据完整、币种为 CNY，再检查账户/日记账/价目表的代码、名称和所有权冲突。只通过原生 ORM 创建最小收入、费用、应收、应付账户、销售日记账和 CNY 价目表；仅为已标记的虚构客户、供应商及商品补充必要的公司属性。已有外部属性或不一致设置直接拒绝，不覆盖、不加载 generic_coa、不触碰 PARTS-B 或用户角色。默认执行只准备会计记录；仅显式传入 `--enable-fulfillment` 且全部预检通过后启用 PARTS-A 的履约策略，模块安装、升级和原有种子命令仍不自动启用。

本地完整流程使用独立命名空间和单次事务：销售报价100件、15%折扣，经理审批；采购补货60；仓库先收30、发70，再收30、发30；财务分别过账5950与2550；仓库退回10，财务按原发票准备并过账850贷项。每个动作切换为对应真实角色，拒绝管理员代办业务。重复执行只核对已完成链路，不重复建单或覆盖用户修改。保留原19标识和40件期初盘点，最终当前库存应为10、净交付90、真实净过账7650。

页面核对使用真实角色账号及现有 HTTP JSON-RPC 验证工具。七个角色分别登录并核对公司、菜单和表单：销售/采购查看授权来源，仓库处理收发货，财务读取销售只读表单、发票和追踪财务字段，PARTS-B 销售不能读到 PARTS-A。另使用本机已有 Chrome、项目内临时用户目录和 Node 内置 WebSocket 驱动页面，保存无凭据的截图与结构化核对结果。明确区分原生 ORM 业务动作、HTTP 权限检查、自动化浏览器页面核对及尚未执行的人工 UAT，不把其中一项包装为另一项。

## 原子性与验证

所有追踪查询只读；会计准备和本地流程各自使用保存点及命名空间锁，失败整体回滚。测试先在回归库运行，根代理再验证开发库，禁止测试方法向开发库写入。M2c 回归保留 M2b 的337项测试和项目辅助测试。会计准备前后核对19标识、期初40的原生移动和 PARTS-B 设置；运行明确的完整流程后允许当前库存从40变10，不再把当前库存40当成永久不变量。重复准备及流程命令返回相同记录标识，不重复创建。

## 边界

本阶段不做外部订单导入、幂等任务、队列、付款、税务本地化、PDF 报表、备份恢复或性能基准。M3/M4 单独规划。
