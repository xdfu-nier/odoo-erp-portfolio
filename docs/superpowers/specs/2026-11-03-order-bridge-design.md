# M3 外部订单接入设计

状态：对 2026-10-26 已确认的方案 0.1 第 5—7 节作实现细化，沿用 REQ-009—012 和 UAT-014—019、023—024。M2 已通过 PR #12 合入；本文件不表示 M3 已实现或验收。

## 目标与选择

工业配件分销企业接收 B2B 订单后，先保存可审计的任务，再生成原生 Odoo 草稿报价。接收方断线、重复发送、缺失主数据及处理器退出均不应产生重复订单或半张报价。

采用独立 `portfolio_order_bridge`，单向依赖 `portfolio_trade`，使用认证 RPC、PostgreSQL 任务及原生 `ir.cron`。同步接收后直接建单会耦合响应与业务失败；外部消息队列会增加本项目部署依赖，均不进入首版。Python、数据库、缓存和运行证据继续保存在项目内。

## 1. 接收契约

公开方法为 `portfolio.import.job.submit_order(payload)`。需要有效内部用户、接入组、目标公司和来源授权。普通销售、未授权来源及伪造允许公司 context 均不能提交。调用 `.sudo()` 不替代实际 UID 的授权。

```json
{"company_code":"PARTS-A","source_code":"B2B","external_order_id":"EXT-001","customer_ref":"CUST-001","currency":"CNY","lines":[{"external_line_id":"1","sku":"BRG-6205","quantity":"100","unit_price":"100.00","discount":"15.00"}]}
```

所有列出的业务字段必填。顶层额外允许 `request_id`、`sent_at` 字符串，两者仅供传输审计，不参与业务摘要。其余未知字段拒绝，调用方不能注入模型 ID、税、销售状态、负责人或任意 ORM 命令。

公司/来源/客户/SKU/外部行号/单号均为区分大小写的非空字符串，禁止首尾空白、控制字符；公司、来源、客户及 SKU 最长 64 字符，单号和行号最长 128 字符。传输字段最长 128 字符。载荷限 64 KiB UTF-8 JSON，商品行限 1—100 行，行号不可重复。错误只返回错误码与字段路径，不回显载荷值。

数量、单价、折扣必须是普通十进制字符串，不接受 JSON number、布尔值、正负号、指数或非有限值。允许前导零与无效尾零；数量大于零且不超过 10^9，单价介于 0 与 10^9，折扣介于 0 与 100。数值的有效小数位最多 6 位，字符串最长 64 字符。规范化不舍入、不使用二进制浮点，`001.000` 与 `1` 相同，零统一为 `0`，行按外部行号字典序排列。使用排序键、紧凑分隔符、UTF-8 JSON 和 SHA-256 产生业务摘要。

纯解析器只校验结构与精确数值。来源解析后校验首版币种 CNY、公司本位币和来源价目表币种一致，并按币种舍入粒度检查单价、按 Odoo Discount 精度检查折扣；不静默截断。处理器解析商品后检查数量能被商品基础单位舍入粒度精确表示。不支持的数量以可定位的失败任务保留，修复映射后可重试。这一分层允许不存在的商品映射先进入失败队列，同时满足禁止精度损失的基线。

返回固定字典 `job_id`、`state`、`sale_order_id`（尚无订单为 false）、`reused`。接收不执行任务、不提交调用方事务。RPC 的标准成功响应提交接收事务。

## 2. 配置、映射与角色

`portfolio.import.source` 绑定公司、稳定外部公司代码、来源代码、CNY 价目表、仓库、业务负责人、处理账号和允许接入账号。公司代码与来源代码组合唯一。设置人员维护配置；创建来源不自动赋予用户角色。修改公司或来源标识不得重解释已接收任务。

客户与商品使用独立映射模型，键分别为来源 + 外部客户编号、来源 + 外部 SKU。映射指向已有有效客户/商品；必须属于来源公司或为允许的共享主数据。数据库唯一约束防止同一来源重复映射；处理时仍验证实际关联对象与原生主数据规则，缺失、失效、歧义及异公司关联均失败，不自动创建主数据。

接入组只能接收和查询被授权来源的任务。处理组采用专用普通销售用户，不能审批、维护设置、操作库存或财务；执行时核对来源指定处理账号、实际公司及负责人。业务销售通过原生报价查看结果，不获得导入载荷或内部错误。来源配置及映射仅向必要角色开放。

所有持久模型有 `company_id`、全局公司规则及关联公司检查。额外显式校验实际用户公司与来源授权，防止 `.sudo()` 或调用方 context 扩权。任务字段的直接 create/write/unlink/copy、审计记录修改和伪造状态均拒绝；内部私有方法只接受已验证的业务参数。

## 3. 幂等与事务

任务唯一键为 `(company_id, source_id, external_order_id)`。同键同业务摘要返回原任务，传输字段变化不产生新任务；同键不同摘要返回冲突，原始载荷、任务与报价保持原样。

来源级接收修订行锁与数据库唯一约束协调真实 REPEATABLE READ 竞争。等待方若读到过期事务快照，向 Odoo 传播序列化异常，由其在新事务中重试；不在同一旧快照中无限重查。不捕获瞬态数据库异常并伪装为业务失败。

处理器以有界批次执行 `FOR UPDATE SKIP LOCKED` 领取 pending 任务，私有入口校验专用处理用户。每个任务的 processing、报价和 done 状态在同一外层事务内；报价创建位于独立保存点。受控业务失败回滚报价及关联写入，在保存点外记录 failed、稳定错误类别、尝试序号、时间和执行人。未知致命异常回滚当前事务，不将任意异常文本写入任务或公开响应。

成功仅生成一张原生草稿 `sale.order`，带来源引用、负责销售、仓库、价目表及明确客户/产品/单位/十进制转换值。价格与折扣来自经验证的载荷，税依据固定首版免税验收政策，不接受载荷注入。创建后由原生主数据检查验证整单。不会确认、审批、预留、采购或开票；后续原生销售流程继续执行 M1/M2 约束。

进程退出导致未提交的 processing、尝试与报价一起回滚，已提交 pending 任务保持可领取。成功后再次执行不会建立第二张报价。人工重试仅允许已授权失败任务，必须提供非空原因；保留原始载荷和原失败尝试，追加执行人/时间/原因后回到 pending。成功任务不可重试，首版无自动重试、外部队列和独立守护服务。

## 4. 界面与本地验证

提供来源/映射设置、授权任务列表与详情、只读原始载荷/结果/尝试记录、失败任务重试原因向导。按钮显示帮助操作，所有权限和状态规则同时覆盖直接 RPC/ORM 路径。调度以专用用户运行，默认不启用自动处理；本地验收显式准备隔离来源和处理账号。

M3 本地样例使用独立命名空间与商品，保留 M1 的 19 个标识及 M2 轴承实际库存 10、净交付 90、净过账 7650 的既有事实。接收、处理和复验通过真实普通用户进行；重复运行只验证/复用已有任务和报价，不重建库存。

## 5. 验证和拆分

1. M3a：无 Odoo 依赖的严格解析与摘要，使用标准库单元测试验证精度、资源上限、未知字段和业务等价性。
2. M3b：来源、映射、任务与权限、持久化接收及数据库幂等；原生角色反例与两个独立事务接收竞争。
3. M3c：保存点处理、失败尝试、人工重试与界面；真实报价、审批约束和中途失败无残留。
4. M3d：两处理器领取竞争、创建后提交前中断恢复、认证 HTTP、隔离本地样例、CI 及发布证据。

每项先失败测试、根代理实际运行，再实现；实现冻结后由根代理执行原生测试，经过独立规格及质量审查后提交。原子性测试用标准 `unittest.TestCase.assertRaises` 在外层清理保存点内捕获异常，并 flush/invalidate 后查询活库，避免测试框架自动回滚掩盖缺陷。

M3 全部退出条件为 UAT-014—019、023—024 的自动化证据、现有进销存回归、实际 GitHub CI 与审查通过。人工 UAT 状态单独记录。M4 的备份恢复与性能仍按原计划执行，不以本设计或代码数量代替验收。
